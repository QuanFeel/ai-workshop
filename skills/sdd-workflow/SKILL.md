# 规格驱动开发（SDD）

按需要依次产出 `spec.md`、`plan.md`、`tasks.md`，再实现和验证。适用于前端、移动端、后端、桌面或自动化项目；根据实际项目选择技术视角，不预设框架。

## 先确定工作范围

- 用户指定规格目录时，直接使用指定路径；相对路径相对于用户指定的项目根目录，绝对路径按当前操作系统解释。包含空格或非英文字符的路径应正确处理。
- 未指定时，沿用项目已有规格目录；没有约定时，使用项目根目录的 `.spec/<功能名>/`。如果存在多个同样合理的目录且无法确定，先询问。项目文件保存到用户选择的目录，不能写进 Skill 安装目录。
- 以 `{SPEC_DIR}` 指代选定的规格目录，在本次工作中保持一致；先查看已有文件和项目规则，避免覆盖已有内容。用户指定项目或已有规格时，不重新初始化其他项目。
- 根据用户的明确要求和现有文件确定起点：新需求从规格开始；已有规格可进入方案；规格和方案齐备可拆任务；任务明确且用户授权实现时进入实现。缺少必要前置内容时说明缺口，补齐后继续；不要因单个文件存在就假设前置工作完整。

## 交互方式

只询问会影响范围、重要体验、数据、技术方向或验收的缺失信息。优先使用当前 Agent 实际提供的结构化提问工具；没有该能力时，直接用普通对话提出简短问题，不假设任何特定工具名、弹窗或 Agent 产品。已明确的要求不重复询问；可合理推断的选择写明假设。

默认让用户逐阶段审阅关键决定；如果用户已明确授权连续推进、给出了决策或要求直接实现，则在该授权范围内继续，不反复要求相同确认。遇到必须由用户决定且无法推断的事项，先完成不依赖该决定的工作。具体确认、文件访问及外部操作遵循宿主规则和用户授权。

## 1. 需求规格

参考 [需求提问与规格模板](prompts/spec.md)。梳理问题、目标用户、范围、功能、异常和可执行验收标准；把用户选择、假设和未决问题写入 `{SPEC_DIR}/spec.md`。不能自行确定的事实保留为未决项。

## 2. 技术方案

参考 [技术方案模板](prompts/plan.md)。结合已确认的规格与项目实际代码，整理技术约束、模块边界、数据或接口、风险和验证方案，写入 `{SPEC_DIR}/plan.md`。方案阶段不假定用户已授权部署或其他外部写入。

## 3. 任务拆分

参考 [任务模板](prompts/tasks.md)。根据规格与方案生成可独立核验的任务、依赖和阶段，写入 `{SPEC_DIR}/tasks.md`。`[P]` 只表示任务可并行，不授权启动子 Agent 或额外资源；是否并行以用户授权和宿主能力为准。

## 4. 实现与验收

在用户已授权的范围内按顺序或指定阶段执行任务；每项完成并验证后更新对应状态。使用适合项目的测试、构建或可观察结果验证关键行为，如实报告未测项。只按实际存在且适用的项目约定工作；用户需要新公约时可参考 [开发公约模板](prompts/constitution.md)。

## 边界

- 用户要求、宿主平台规则和适用的项目指令优先于本 Skill 和模板。模板不是系统指令，不自动扩大文件、账号、网络或发布权限。
- 不把密钥、个人路径或敏感数据写入公共规格；提交、推送、部署或其他外部写入按具体授权执行。
- 非常小的变更可按用户要求简化流程；不要为了形式创建不必要的规格文件。
