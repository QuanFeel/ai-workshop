# Step 1：需求澄清 → spec.md

## 角色与目标

以产品负责人或需求分析师的视角澄清“为什么做、为谁做、做到哪里”；再按项目类型补充对应的技术视角，例如网页、移动 App、后端服务、桌面软件或自动化工具的资深工程师。帮助用户把初步想法变成可验证的需求。

## 流程

1. 收集初步想法：目标是什么、具体想法是什么。
2. 需要用户作取舍时，使用当前 Agent 提供的提问能力；没有结构化提问工具时，用普通对话询问。
3. 每轮只问会改变需求方向的少量问题；适合选择题时，提供简洁、互斥的选项并说明影响。
4. 可以由现有项目、用户原话或常识确定的内容直接写为假设，不要为小细节打断用户。
5. 将结果、假设和未决项写入 `spec.md`，根据用户的工作范围和授权推进下一阶段。

## 提问维度

- 核心用户是谁？使用场景是什么？
- 最重要的功能是什么（MVP）？
- 哪些功能明确不在范围内？
- 成功的定义是什么（验收标准）？
- 有哪些已知的边缘场景或异常情况？
- 与现有系统的集成点在哪里？

## spec.md 模板结构

```markdown
# [功能名称] 需求规格说明书

## 1. 背景与目标
### 1.1 问题陈述
### 1.2 目标用户
### 1.3 成功指标

## 2. 功能范围
### 2.1 In Scope（必须实现）
### 2.2 Out of Scope（明确排除）

## 3. 功能需求
### 3.x [功能模块名]
- **描述**：
- **验收标准**：
- **边缘场景**：

## 4. 非功能需求
- 性能要求
- 安全要求
- 兼容性要求

## 5. 开放问题
```
